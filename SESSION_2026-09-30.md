## Key design decisions

### Single-process mutual signing
`Log.append()` requires both wallets in the same Python process. Cross-process / cross-machine signing (`ProposeLog` + `CounterSignLog`) deferred to v0.3.0 per README roadmap. v0.2.0 is the strong case; v0.3.0 adds the realistic case.

### Log_id is a storage namespace, not cryptographic content
The entry_hash deliberately doesn't include `log_id`. Two entries with identical fields but different log_ids hash identically. log_id lives in the SQL `WHERE` clause. This keeps the hash chain portable across storage backends.

### Hash chain is mandatory from sequence 1
`entry.parent_hash` is None for the genesis entry only. Sequence 2+ must reference sequence N-1's hash. Verified by `verify_chain`.

### Tampering test pattern
Tests that simulate tampering (`test_verify_chain_detects_hash_tampering`, `test_verify_signatures_fails_when_sig_removed`) reach into `storage._conn` directly to mutate rows. Documented as internal-channel use only. Comments call out `noqa: SLF001`.

## Notes for future sessions

- If you change the entry-hash algorithm (e.g., to use SHA-3 or BLAKE3), every existing entry becomes invalid. Don't change it after v1.0.0 without a migration path.
- The `sqlite.Row` factory on the connection is required — without it, `_row_to_entry` fails on column access. Comment in `storage/sqlite.py` notes this.
- `xrpl-py` Wallet in 4.x doesn't have `.sign()` or `.verify()` methods. Use `xrpl.core.keypairs.sign` and `is_valid_message` directly. (Captured in signing.py docstring.)
- The scanner script's `Path.relative_to` crashed when called with paths outside the repo root. Fixed by guarding the conversion with `startswith(str(root))`.
