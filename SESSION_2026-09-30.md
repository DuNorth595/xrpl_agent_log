## Headline honesty: what is real vs. what is not

This package's three guarantees:

| Guarantee | How it's tested | Real? |
|---|---|---|
| **Hash-chain integrity** (any entry mutation breaks the chain) | `test_verify.py::test_verify_chain_detects_hash_tampering` — mutates a SQLite row directly and asserts `verify_chain` fails | Real — direct DB write, no fudging |
| **Mutual signature integrity** (both parties must sign) | `test_signing.py::test_verify_entry_signature_*` — uses real `xrpl.wallet.Wallet.create()` and real `xrpl.core.keypairs.is_valid_message` | Real — actual secp-256k1 ECDSA over the entry hash |
| **On-chain anchor lookup** (tx hash actually resolves on the ledger) | `test_verify.py::test_verify_on_chain_anchor_detects_missing_tx` (offline fake hash) + **`test_integration_ledger_live.py::test_end_to_end_live_anchor`** (live testnet) | Real — see the live section below |

What is **NOT** yet tested:
- Multi-party logs (3+ parties). The package supports two-party mutual logs today; N-party generalization is a v0.4.0 goal.
- Cross-log verification (one log referencing an entry from another log's tx hash). v0.5.0 work.
- Anchor memo payload parsing. The current script writes a hex memo; reading it back and verifying it round-trips is a v0.3.0 addition.

## Key systems now in place

### Public API (`src/xrpl_agent_log/__init__.py`)
- `Log` — orchestrator (append, latest, replay, count)
- `SigningPair` — two-party mutual attestation
- `Entry` — the unit of commitment (sequence, parent_hash, agent_a_did, agent_b_did, intent, on_chain_tx_hash, params, timestamp, entry_hash, sig_a, sig_b)
- `SQLiteStorage` — append-only backend with `log_id` namespace
- `verify_chain`, `verify_signatures`, `verify_on_chain_anchor` — three independent integrity checks

### CLI (`python -m xrpl_agent_log`)
- `--version` — prints `xrpl_agent_log v0.2.0a1` and lists the public API
- `--demo` — creates an in-memory log, appends three entries, verifies all three layers, prints `Demo PASSED`
- No-args invocation mirrors `--version` (same convention as `xrpl_agent_id`)

### Storage model
- Single SQLite file with two columns of interest: `(log_id, sequence)` composite primary key, plus all entry fields denormalized
- `UNIQUE(log_id, sequence)` enforces no-gap, no-dup monotonic ordering
- Storage owns *append-only* discipline; `verify_chain` owns the cryptographic chain discipline — the two layers together give "tamper-evidence"

### CI (`.github/workflows/ci.yml`)
- Matrix: Python 3.9, 3.10, 3.11, 3.12
- Runs: `pre-commit run --all-files` → `pytest tests/` → CLI smoke test
- `ubuntu-24.04` pinned
- `actions/checkout@v7`, `actions/setup-python@v7`
- Live XRPL testnet tests stay self-skipped unless `RUN_LIVE=1`

### Security: two layers of seed-secret defense
- **Local:** `.pre-commit-config.yaml` runs `scripts/check_no_seeds.py` on every commit
- **CI backstop:** workflow runs `pre-commit run --all-files` before pytest

## Honest disclosure

A few things worth flagging before any public release:

1. **Same-address parties are not supported.** The current `attach_signature` checks the wallet's address against `agent_a_did` and `agent_b_did`; if both DIDs end with the same address, only one signature slot gets populated and the append fails. This is by design — a mutual log with two distinct parties is the point — but the live script *almost* tripped on it during development. Fix was to fund two faucet wallets and use them as A and B. The behavior is now well-defined: two distinct addresses → mutual log; same address → raises ValueError.
2. **The integration test funds wallets on every run.** That's wasteful but predictable. A future optimization: cache a funded wallet pair at session start.
3. **On-chain anchor reads are not cached.** Every `verify_on_chain_anchor` call hits the network. For audit scripts that re-verify thousands of entries, batch + cache would matter. Not blocking for v0.2.0.
4. **The live-anchor script writes to and deletes `live_anchor_verify.db` at the repo root.** It's excluded from git by `.gitignore` but if you run it from a different cwd, it will create the DB wherever invoked.
